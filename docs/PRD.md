# PRD: Personal Workout Tracker

**Working title:** local-first-workout-tracker-pwa (repo name; product name not finalized)
**Status:** Specification for implementation (revised: platform-neutral, MVP re-cut — see [ADR 0005](decisions/0005-mvp-scope-and-platforms.md))
**Platform:** installable, offline-capable PWA for iOS/iPadOS, Android and desktop browsers
**Primary user:** a single user, the developer
**Principle:** local-first, offline-capable, no mandatory account, no subscription, no required backend

Related docs: [data model](data-model.md) · [import schema](import-schema.md) · [architecture](architecture.md) · [roadmap](roadmap.md) · [backup & restore](backup-restore.md) · [PWA install](pwa-install.md) · [browser limitations](browser-limitations.md) · [ADRs](decisions/)

## 1. Executive Summary

A personal, local-first workout tracker: fast set logging, routines, history, progress, and a documented import format so that training plans generated by an external AI assistant (or exported from other apps) become usable routines in minutes. No backend, account, or paid API is needed for core functionality.

### Goals

1. Be the everyday workout logger — including importing existing history (e.g. from Hevy) so previous values and PRs are not empty.
2. Make recording a set during a gym session as fast as possible.
3. Never lose workout data; keep it exportable in a documented format.
4. Import structured plans from AI assistants (the differentiator) and, later, online sources.
5. Work offline after first load, on iOS/iPadOS, Android and desktop.
6. Cost nothing to run: static hosting, no accounts, no paid APIs.

### Non-goals

Social features, a commercial SaaS, a trainer marketplace, medical/rehab advice, AI coaching with recurring inference cost, a health platform, a native app (unless PWA limits prove unacceptable), cloning every Hevy feature.

## 2. Users, Platforms, Assumptions

The primary user is a senior software engineer who logs strength training, mostly on a phone at the gym (one-handed, between sets), and sometimes reviews or plans on a laptop. Utility, speed, data ownership and maintainability beat feature breadth.

### 2.1 Supported platforms

| Target | Support level |
|---|---|
| iOS / iPadOS Safari, installed via Add to Home Screen | **Primary, most constrained.** Called out wherever it differs. |
| Android Chrome, installed | **Primary.** |
| Desktop Chromium (Chrome, Edge), installed or tab | Primary for review/planning. |
| Desktop Safari (macOS, Add to Dock or tab) | Supported. |
| Desktop Firefox | Works as a browser tab; cannot be installed. |

UI is phone-first (one-handed, large targets) and responsive up to desktop widths. Features depend only on APIs available on all primary targets, or degrade gracefully (§2.2).

### 2.2 Platform differences (design for the weakest, enhance where available)

Details and verification status: [browser-limitations.md](browser-limitations.md).

| Area | Rule |
|---|---|
| Background timers / alerts | A suspended PWA cannot be guaranteed to fire an alert on any platform, iOS worst. The rest timer stores `endsAt` and recomputes on return; alerts are foreground-only. No claim of locked-screen alarms until verified on device. |
| Haptics | `navigator.vibrate` works on Android, not on iOS. Haptics are an optional enhancement; every cue must also have a visual (and optional audio) form. |
| Install flow | iOS: Safari Share → Add to Home Screen (no install prompt). Android/desktop Chromium: install prompt/menu. macOS Safari: Add to Dock. Firefox desktop: none. See [pwa-install.md](pwa-install.md). |
| Storage | Browser storage can be evicted. Request persistent storage (`navigator.storage.persist()`) and show its status. On iOS the installed app and the Safari tab may have **separate** storage; the user must pick the installed app and keep using it. |
| Origin | IndexedDB is bound to the origin. Production uses a **stable origin** (`brunocpf.github.io` on GitHub Pages); moving host or domain requires exporting a backup first and restoring it afterwards. Other project sites share that origin, so DB and cache names are app-specific. |
| File save | Mobile: Web Share API with files (→ Files, iCloud, Drive), where `navigator.canShare({files})` is true. Desktop: download via anchor. Never depend on the File System Access API. |
| Wake lock | Use Screen Wake Lock during an active workout where available; absence is not an error. |

### 2.3 Assumptions to validate (Phase 0)

- IndexedDB persists in an installed iOS PWA and an installed Android PWA across weeks of use.
- The user manages their own backups.
- A self-written seed catalog of ~100 exercises is enough for MVP; a larger catalog is later work.
- The user can obtain a real Hevy export (needed to design the Hevy importer).

Do not add accounts, a backend, or paid APIs merely because commercial apps have them.

## 3. Product Principles

1. **Local-first.** The local database is the source of truth. Logging, history, search, progress and plan import work offline.
2. **Fast interaction.** Optimize starting a workout, completing a set, editing weight/reps, seeing previous values, the rest timer, adding/replacing an exercise, finishing.
3. **Data ownership.** All essential data is exportable in a documented, versioned format.
4. **Untrusted imports.** Imported content is validated, previewed, and confirmed — never executed or rendered as HTML.
5. **Simplest thing that works.** PWA capabilities first; native code or a backend only for a concrete requirement and an ADR.
6. **Separation of concerns.** Catalog, programs, routines, schedule, sessions, sets, metrics, and external formats stay separate. Changing a routine never rewrites completed workouts.

## 4. Scope and Priorities

### P0 — MVP (a vertical slice the user can train with)

1. Seed exercise catalog: ~100 exercises, stable ids, self-written text, search by name/alias. No wger dependency.
2. **Routines via JSON import**: paste/file, schema validation, minimal preview, exercise matching (exact/alias/normalized; unresolved ones resolved manually), explicit confirm. This is the fastest path to routines and the differentiator, so no routine-builder UI in P0. Blank workouts are also supported.
3. **Workout logger**: start from routine or blank, log weight/reps/complete, add/remove sets and exercises, previous values, finish.
4. **Rest timer** (`endsAt`-based, foreground alerts).
5. **History**: list and session detail; edit/delete completed sessions (§5.3).
6. **Interrupted-session recovery.**
7. **Full JSON backup export and restore.**
8. **Installable, offline PWA** with safe updates and stable origin.
9. Settings: weight unit, default rest, auto-start timer, theme, week start, backup reminder.

### P1 — in order

1. **Hevy history import** (promoted: without imported history, previous values and PRs stay empty for weeks).
2. Routine builder UI (and program grouping/editing).
3. Custom exercises UI.
4. Exercise detail pages and guides.
5. PRs and basic charts.
6. AI prompt generator.
7. Calendar.

Then: online-plan import assistance, CSV import/export, supersets, warm-up/drop/failure set UI, RPE/RIR UI, plate calculator, muscle-group volume, monthly statistics, body measurements, routine folders/favorites, program scheduling, exercise substitutions, progression rules, wger catalog evaluation.

### P2

Progress photos, native notifications/native wrapper, widgets, cloud backup/sync, shareable program URLs, external AI API, AI progression suggestions, Apple Health.

### Out of scope

Social feed, followers, public profiles, subscription billing, mandatory auth, mandatory backend, auto-generated workouts without approval, medical advice.

## 5. Information Architecture and Core Behaviors

Top-level destinations (workout execution over analytics): **Home, Routines, History, Exercises, Progress** (tabs may be hidden until their feature exists). Settings and backup are in a secondary menu.

### 5.1 Home

Primary "Start workout" action, resume banner if a session is active, quick-start for saved routines, recent workouts, weekly count (using the configured week start). Never an analytics dashboard that delays starting.

### 5.2 Routines

List/start/delete/duplicate imported routines (P0); Import entry point; create/edit builder (P1).

### 5.3 History

Reverse-chronological sessions; detail shows date/time, duration, routine, exercises, sets, derived volume, notes.

- Past sessions are read-only by default; editing is an explicit action.
- **Edit or delete a completed session** requires explicit confirmation; derived data (volume, PRs) is recomputed because it is never stored as the only representation.
- **Log a past workout retroactively** (choose date/time, then log as normal).
- **Discard an active workout** = delete it after confirmation.

### 5.4 Time and calendar semantics

Each session stores its IANA time zone and ISO 8601 timestamps. "Day", "week" and "streak" use the session's *local* day in that zone. The week start is configurable (default Monday, or from locale). Travel or DST must not move a workout to another day.

## 6. Exercise Catalog

### 6.1 Metadata

Stable id, name, aliases, primary/secondary muscles, equipment, exercise type (weighted reps, bodyweight reps, duration, distance), optional movement pattern, instructions, form cues, media, source/license, custom flag, archived status. Types: [src/lib/types.ts](../src/lib/types.ts), [data-model.md](data-model.md). Imported/seed data may be incomplete; the UI tolerates missing fields.

### 6.2 MVP catalog

~100 common strength exercises, ids stable forever (they are referenced by history, backups and import files), text written for this project (no copied descriptions, no media). Search is offline, case/diacritic-insensitive over name and aliases. Filters (muscle, equipment, type, favorites only) combine with the text query; the picker lists Favorites, then Recent (last 5 completed sessions), then all.

### 6.3 Later

Custom exercise UI, exercise detail pages (instructions, history, PRs, external guide link), media only where legally usable (missing media must never show a broken placeholder). Evaluate **wger** as a larger catalog source only after P0: verify API/schema, license per data type (text, images, video differ), record attribution ([attribution.md](attribution.md)), and never require network for lookups.

### 6.4 Merge and rename

History references exercises by id and snapshots the name, so **renaming never alters history display** of past sessions. A **merge** (e.g., duplicate custom exercises) re-points history to the surviving id after confirmation, keeping the old name as an alias. Archiving hides an exercise without deleting history.

## 7. Programs and Routines

A **program** is a plan (e.g. Upper/Lower); a **routine** is one reusable workout; a **scheduled workout** is an intended occurrence; a **session** is what actually happened. P0 stores imported programs as routines (program metadata kept for display); the builder, scheduling and progression are P1.

### 7.1 Semantics (all phases)

- Starting a session copies the routine's prescription into each session exercise (ADR 0004); later routine edits never change that session or any past one.
- Changes during a session affect only that session unless the user explicitly saves them to the routine (P1).
- Programs and imported routines remain editable after import (P1 builder).
- Scheduling is advisory, simple weekly assignment (P1).

### 7.2 Builder (P1)

Add/remove/reorder/replace exercises, sets, rep ranges, optional target weights, rest, notes, duplicate and rename routines, reorder within a program.

## 8. Workout Logging

The highest-priority UI.

### 8.1 Start

From a saved routine, from Home, or a blank workout. Only **one active session** exists at a time.

### 8.2 Active screen

Shows per exercise: name, previous performance, set number, weight, reps, completion, notes; plus rest timer, add set/exercise, finish. Recording a set never requires leaving the screen.

### 8.3 Set logging

- Weight and reps independently editable; prefilled from the previous matching set (§8.4) or the routine target.
- **Completing a prefilled set is one tap.** Editing a value never completes the set; completion is undoable.
- Quick duplicate of a set; undo for recent destructive actions; keyboard dismissal keeps input.
- Optional per set: RPE, RIR, duration, distance, notes (UI for RPE/RIR is P1; the model supports them from v1).

### 8.4 Previous values

Each set row shows the previous value from the most recent *completed* session containing that exercise (setting for "same routine" is P1). Alignment:

- Set N ↔ previous set N, matched within the same set-type group (working sets with working sets, warm-ups with warm-ups).
- Extra sets beyond the previous count fall back to the last previous set of that type.
- With no history, show nothing and prefill from the routine target if any.

### 8.5 Set types

The model and import format support normal, warm-up, drop and failure sets **from v1**. P0 UI logs normal sets and can mark a set as warm-up; full UI for warm-up/drop/failure and supersets comes later. Warm-ups never count toward volume or PRs.

### 8.6 Finish

Persist data, record `endedAt` and duration, show a compact summary, make the session appear in History immediately.

### 8.7 Interrupted workouts

Handle accidental navigation, reload, browser suspension, device lock, connectivity loss, duplicate completion. Persistence is **write-through on every mutation** (ADR 0004); never rely on an unload handler. Reopening restores the active session, including a running rest timer. **App updates never reload the page during an active session** ([ADR 0003](decisions/)).

## 9. Rest Timer

- Configurable default, per-exercise override, auto-start after completing a set (setting), manual start, pause/resume, ±time, skip.
- State lives on the session: `endsAt` timestamp (+ pause bookkeeping). Remaining = `max(0, ceil((endsAt − now)/1000))`. The display ticks periodically but correctness never depends on ticks.
- Foreground alerts: visual, optional sound, and vibration where supported (Android). See §2.2 for background limits; the UI says honestly that alerts may not fire while the app is backgrounded.
- On return from background, the timer shows the correct remaining time (or "done").
- If locked-screen alarms become a hard requirement, evaluate a native wrapper by ADR; push is not a substitute for local timer alarms.

## 10. Progress Tracking

All derived from raw completed sets; nothing derived is the only copy.

### 10.1 Definitions

Only completed, non-warm-up sets count. Weights compare in kg internally.

| Metric | Definition |
|---|---|
| Set volume | `weight × reps` (weighted-reps exercises only). Bodyweight and duration exercises are tracked separately. Unilateral: reps per side, not doubled. |
| Session volume (per exercise) | Sum of set volumes in one session. |
| Max weight PR | Heaviest weight with ≥ 1 rep. |
| Rep-max PR | For each rep count 1–12: heaviest weight lifted for exactly that many reps. |
| Estimated 1RM | Epley `weight × (1 + reps/30)`, valid for 1–12 reps only; otherwise not computed. An estimate, not a measured max. |
| Best session volume | Highest session volume for an exercise. |

A set is a *new PR* only if it strictly beats the previous best at that point in time (ties don't count). Editing/deleting a session recomputes PRs from raw data.

### 10.2 Display

- P1: per-exercise history, PRs, basic charts (e1RM, max weight, volume over time) with date ranges.
- Later: weekly sets/volume by muscle group (documented, estimated attribution), frequency, calendar, body measurements.
- Avoid gamification that penalizes rest days.

### 10.3 Units

Kg internally; the display unit is a setting (kg/lb). Values entered in a display unit must round-trip (enter 135 lb → shows 135 lb). Display rounds to at most 2 decimals with trailing zeros trimmed; stored values are not rounded. Details: [data-model.md](data-model.md), ADR 0004.

## 11. AI-Assisted Plan Import (P0 core)

The app needs no AI API: the user asks any assistant for JSON in the documented format and imports it.

### 11.1 Workflow

1. User copies JSON from an assistant (or opens a `.json` file).
2. App parses and validates against schema v1 (size-limited).
3. Exercises resolve against the local catalog: exact id → exact alias → normalized name → (optional) fuzzy *suggestions* → manual selection. Fuzzy never silently substitutes a different movement.
4. **Preview** (minimal in P0): program/routine names, exercises with match status (exact / suggested / unresolved), sets, rep ranges, rest, notes, errors and warnings. The user can resolve unmatched exercises, remove exercises, rename the program.
5. Errors block saving; warnings don't. Nothing is saved or activated without explicit confirmation, and a failed import leaves existing data untouched.

The preview also lets the user rename routines, reorder exercises and edit each exercise's sets with the prescription editor; those edits are layered over the draft and are exactly what Confirm saves (Cancel saves nothing).

### 11.2 Input methods

P0: paste JSON, import `.json`. P1: Markdown with a fenced JSON block (explicit extraction step, never guessing at prose), CSV, article text, URL with assisted extraction.

### 11.3 Schema

The format is a public contract independent of the IndexedDB schema: program metadata, routines, ordered exercises, set counts, rep ranges, optional target weight/rest/set type/RPE/RIR/notes, optional weekly schedule, source/attribution; unresolved names allowed. Version 1; unsupported versions are rejected with a clear message. Authoritative spec, example and limits: **[import-schema.md](import-schema.md)**.

### 11.4 Prompt generator (P1)

"Generate a plan with AI" copies a prompt (schema, allowed exercise ids/names, user constraints, "JSON only", "don't invent ids"). No workout data is included unless the user explicitly opts in; nothing is uploaded automatically.

### 11.5 Plan quality

The importer validates structure, not training quality. It may warn (implausible frequency, very high volume, missing rest, unavailable equipment) but never claims a plan is safe or optimal, and gives no medical advice.

## 12. Other Imports (P1)

### 12.1 Hevy history (first P1 item)

Adapter: `Hevy export → normalized records → validation → preview → local database`.

- **Format and mapping:** designed from a real export (CSV); see [docs/hevy-import.md](hevy-import.md) and ADR 0006. (Hevy references: hevyapp.com, api.hevyapp.com/docs.)
- Preserve dates, exercise names, sets, reps, weights, supported set types, notes; report unsupported fields; map Hevy exercise names to catalog ids with manual resolution of the unmatched; create custom exercises on request.
- Detect duplicates; never overwrite history silently; the core app never depends on Hevy's API.

### 12.2 Online plans and CSV

URL import cannot be assumed to work (CORS, JS-rendered sites); always offer paste-text. Decision (ADR 0008): the app does not fetch URLs; the user pastes the page text and the URL is kept only as source attribution. Preserve source URL/attribution; don't bypass access controls. CSV export of history (stable ids, timestamps) and CSV import with explicit column mapping and deliberate duplicate handling come after Hevy.

## 13. Backup, Export and Restore (P0)

IndexedDB is persistent, not a backup. Planned format and UX: [backup-restore.md](backup-restore.md).

- **Full backup**: versioned JSON of all user data (custom exercises, routines/programs, schedule, sessions, sets, settings) plus app and format versions. Independent of the Dexie schema.
- **Save**: Web Share API with a file on mobile (→ Files/iCloud/Drive); download on desktop or when sharing isn't available.
- **Restore** validates the whole file with Zod before touching the database; any error → clear message, **nothing changes**. Full restore requires an explicit confirmation naming what will be replaced. Program/routine-only import (§11) is a different operation that only adds data.
- **Reminder**: non-blocking banner when the last backup is older than N days (default 14) or more than N sessions ago (default 10), whichever comes first; configurable, never shown during an active workout.
- Backups never fail silently: success shows size and date; failure shows the cause.

## 14. Technical Architecture

### 14.1 Stack

TypeScript · SvelteKit 3 / Svelte 5 (runes) static SPA (`adapter-static`, SSR off) · Dexie (IndexedDB) · Zod 4 · Vite · hand-written service worker + web manifest · Vitest · ESLint (incl. `svelte/no-at-html-tags`) · Playwright e2e. Charts: a lightweight library, only when needed. See ADRs [0001](decisions/0001-local-first-pwa.md), [0002](decisions/0002-sveltekit.md), [0003](decisions/), [0004](decisions/).

### 14.2 Boundaries

Domain logic lives in flat modules under `src/lib/` (e.g. `storage/db.ts`, `storage/sessions.ts`, `imports/…`), imported as `#lib/<file>`; components only call them. A module file is added when there is code for it. See [architecture.md](architecture.md).

### 14.3 Persistence

Dexie with explicit schema versions; never drop user data on update; test migrations against representative old DB states and failed upgrades. The active session is an in-memory `$state` object written through to Dexie on every mutation; details in ADR 0004.

### 14.4 PWA

Valid manifest with PNG and maskable icons; HTTPS; precached app shell with navigation fallback; offline start after first load; safe-area and viewport handling; deferred service-worker updates with an "update available" banner (suppressed during an active workout); CSP; `BASE_PATH` for sub-path hosting; GitHub Pages deploy workflow (any static HTTPS host with SPA fallback also works); app-specific IndexedDB name and cache prefix. Details in [ADR 0003](decisions/). The service worker never caches dynamic responses indiscriminately.

### 14.5 Backend policy

None. A backend (cloud backup, sync, shared plans, AI inference, push) needs a concrete requirement and an ADR.

## 15. Data Model

Types: [src/lib/types.ts](../src/lib/types.ts). Entity descriptions, conventions and rules: [data-model.md](data-model.md); persistence decisions: [ADR 0004](decisions/). Invariants this PRD relies on:

1. Stable ids, never names, as foreign keys; exercise names are snapshotted in sessions.
2. Routine prescription is copied into each session exercise; routine edits never rewrite history.
3. Raw sets are stored; aggregates are computed. Set types and optional RPE/RIR/duration/distance exist from v1.
4. Weight in kg internally; ISO 8601 timestamps; session `timeZone`.
5. One active session; rest timer state on the session.
6. No accounts or sync fields.

## 16. Import Schema

The program import format is a versioned public contract, separate from the internal schema: [import-schema.md](import-schema.md). Summary: JSON with `schemaVersion` and a `program` containing routines of ordered exercises (id or name, sets, rep range, optional weight/rest/set type/RPE/RIR/notes), optional weekly schedule and source. Validated with Zod; max size, no code execution, no HTML rendering, no automatic media fetching, no overwrite without confirmation; unresolved exercises are resolved in preview, never invented. Previously exported files must keep working across versions (fixture tests).

## 17. Progression Rules (P1+)

Configurable, transparent, user-controlled; never automatic in the first releases. Starting point: optional double progression ("hit the top of the rep range on all sets → suggest +increment"), each suggestion explaining its rule. Percentage, RPE-based and deload rules are future work.

## 18. UI and Interaction

- Compact, polished, dark-mode capable; large touch targets; primary actions reachable by thumb; no hover-only interactions; no decorative excess.
- Safe areas (iOS notch/home indicator); virtual keyboard must not hide the active set (iOS especially); no accidental horizontal scroll; keyboard and pointer support on desktop; responsive layout up to desktop width.
- Clear states for: first-run database setup, migration, offline, import validation/failure, backup/restore, update available, unsupported capability (e.g. no persist, no share).
- Accessibility: semantic HTML, labelled inputs, sufficient contrast, completion not conveyed by color alone, reduced-motion support, actionable error messages.
- Logging never waits on optional content (catalog extras, media, charts).

## 20. Privacy and Security

No account, ads, or analytics SDK; no automatic upload of any data; external AI use is user-initiated and the user chooses whether any history is included in a prompt; import/export is explicit; no secrets in client code; backups are never exposed at public URLs. CSP and `svelte/no-at-html-tags` enforce no HTML injection from imported text. If sync or built-in AI is ever added, document exactly what leaves the device and obtain consent.

## 22. Testing Strategy

### 22.1 Automated

- **Unit/domain (Vitest):** volume, e1RM, PR detection (§10.1), previous-value alignment, alias/exercise matching, routine-to-session copy, import validation, unit conversion and round-trip, week/day boundaries in time zones, rest timer, migrations, backup round-trip.
- **Import fixtures:** valid; missing fields; unsupported version; bad rep ranges; non-positive sets; unknown/ambiguous exercises; duplicate routine ids; malformed JSON; oversize; unsupported fields; no schedule. Failed imports must not leave partial data.
- **Persistence:** completed sets survive reload; active session resumes (with timer); routine edit doesn't touch history; backup → restore preserves data; failed restore changes nothing; migrations preserve data.
- **E2E (Playwright):** projects for **Chromium desktop, Pixel emulation, and WebKit/iPhone emulation**; cover the vertical slice (import routine → start → log → reload → resume → finish → history), offline reload, and backup/restore.

### 22.2 Real-device checks (still required)

Emulation does not reproduce iOS storage eviction, standalone-mode behavior, suspension, the keyboard, or Share Sheet. Run the checklists in [pwa-install.md](pwa-install.md) on a real **iPhone/iPad (installed from Safari)** and a real **Android phone (installed from Chrome)** before declaring P0 done, and record findings in [browser-limitations.md](browser-limitations.md).

Full verification: `npm run check && npm run lint && npm test && npm run build && npm run test:e2e`.

## 23. Acceptance Criteria (P0)

**Install and offline**
- [ ] Installs on iOS/iPadOS (Safari), Android (Chrome), and desktop Chromium; runs standalone.
- [ ] After first load, the app launches and works fully offline on Chromium, Android and iOS (Playwright for Chromium/WebKit emulation; real devices for Android and iOS).
- [ ] Cold offline launch to resumed session < 2 s on a mid-range phone.
- [ ] An app update never reloads during an active session; banner appears afterwards.
- [ ] Persistent-storage status is shown; its absence is explained.

**Logging**
- [ ] Start from an imported routine or a blank workout.
- [ ] Completing a prefilled set takes 1 tap; completion can be undone; editing doesn't complete.
- [ ] Previous values are shown per set with the alignment rules in §8.4.
- [ ] A completed set survives force-quit, reload and device lock.
- [ ] Rest timer is correct after backgrounding and reload.
- [ ] Add/remove sets and exercises; discard an active workout after confirmation.
- [ ] Finished sessions appear in History; past sessions can be edited/deleted only after confirmation; retroactive logging works.
- [ ] Routine edits/deletes never change past sessions.

**Catalog and import**
- [ ] ~100 seed exercises searchable offline by name/alias.
- [ ] A valid JSON plan can be pasted or loaded from a file; invalid input yields actionable errors.
- [ ] Unresolved exercises require manual resolution; nothing saves without confirmation; failed import changes nothing.

**Backup**
- [ ] Full backup exports (Share on mobile, download on desktop); restore validates first, confirms, and on any error changes nothing.
- [ ] Backup → wipe → restore preserves all sessions, sets, routines, custom data, settings.
- [ ] Reminder appears per policy, never mid-workout.

**Quality**
- [ ] No data loss during navigation, reload or suspension.
- [ ] Usable one-handed on a phone and responsive on desktop; handles the iOS keyboard and safe areas.
- [ ] `npm run check && npm run lint && npm test && npm run build && npm run test:e2e` pass.
- [ ] Timer limitations are stated honestly in the UI and in docs.
- [ ] No feature requires a network call or backend.

## 24. Implementation Plan

Vertical slice first: **the logger must not wait for the builder or for import.** Each phase leaves a runnable app.

**Phase 0 — Validation.** Confirm install + IndexedDB persistence on a real iPhone/iPad and Android phone; confirm the production origin (GitHub Pages, `brunocpf.github.io`); decide seed-catalog sourcing (self-written); **obtain a real Hevy export**; confirm the ADR 0003/0004 foundations.

**Phase 1 — Shell and storage.** Navigation, theme, settings, Dexie schema/migrations, seed catalog (~100 exercises) with search, PWA shell, CI.

**Phase 2 — Logger vertical slice.** Blank workout (and a fixture routine in dev) → pick exercises → log sets → persist → reload → recover → finish → history. Previous values and the rest timer land here. Playwright covers it.

**Phase 3 — Routines via import.** Schema v1 validation, minimal preview, exercise matching, save routines, start from routine, routine list/delete.

**Phase 4 — Backup, hardening, P0 release.** Full backup/restore, backup reminder, persist() status, update banner, edit/delete/retroactive sessions, device checklists on iOS and Android. P0 complete.

**Phase 5 — Hevy import.** Adapter, mapping, preview, duplicate detection.

**Phase 6 — Authoring.** Routine builder UI, custom exercises UI, exercise detail/guides.

**Phase 7 — Insight.** PRs, charts, AI prompt generator, calendar.

**Phase 8 — Everything else** from P1/P2, ordered by actual use.

## 25. Coding-Agent Working Rules

Also summarized in [AGENTS.md](../AGENTS.md).

1. **Vertical slices.** Start routine → log set → persist → reload → recover → finish → history, then expand.
2. **Inspect before editing.** Read the structure and ADRs; reuse tooling; avoid new dependencies; explain persistence decisions.
3. **Testable logic.** Progress, matching, import validation and persistence live in `src/lib`, not in Svelte components, and have tests. Never use `{@html}` with imported text.
4. **No premature infrastructure.** No backend, accounts, paid APIs or sync without a concrete requirement and an ADR.
5. **Preserve data.** Data loss is a serious defect: test migrations, interrupted sessions, restore; use `$state.snapshot` before Dexie writes.
6. **Keep the app usable** after each phase and run the full verification command.
7. **Document** decisions (ADRs), data model, import schema, backup/restore, install steps, browser limitations, attribution — alongside the code.
8. **Don't overbuild.** Prefer the simplest implementation; add module files when there is code for them.

## 26. Open Decisions

1. **Name:** repo name only; final product name open.
2. **Production origin:** currently GitHub Pages (`brunocpf.github.io`). A custom domain later would cost a manual export/restore, so decide before real data accumulates.

## 27. Definition of Success

The developer can install the app on their phone, import or create a plan, log workouts quickly with previous values and a rest timer, close and reopen without losing anything, review history and strength progress, bring in their Hevy history, export and restore everything, use it offline on their phone and (when wanted) on a laptop. The criterion is not feature parity with commercial trackers but being able to train with this app indefinitely, with reliable local data and no recurring cost.
