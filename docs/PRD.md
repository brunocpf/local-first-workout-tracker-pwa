# PRD: Personal Workout Tracker

**Working title:** local-first-workout-tracker-pwa (repo name; product name not finalized)  
**Document type:** Product Requirements Document  
**Status:** Initial specification for implementation  
**Primary platform:** iPhone, delivered as an installable Progressive Web App (PWA)  
**Primary user:** A single user, the developer  
**Implementation approach:** AI-assisted development with a coding agent  
**Product principle:** Local-first, offline-capable, no mandatory account, no subscription, no required backend

---

## 1. Executive Summary

Build a personal workout-tracking application that replaces the functionality the developer currently uses in Hevy, without the subscription cost or the complexity of features that are not needed.

The app should provide a polished, mobile-first experience for logging strength-training workouts, following customizable routines, tracking long-term progress, consulting exercise guides, and importing training plans from AI assistants or online sources.

The defining capability is that the user can ask an external AI assistant to generate a personalized training plan in a documented, structured format, import it into the app, validate and customize it, and immediately begin tracking progress.

The application must not require an AI API, backend server, user account, or recurring infrastructure expenditure for its core functionality.

### Product goals

1. Replace Hevy for everyday personal workout logging.
2. Make recording sets fast and convenient during gym sessions.
3. Preserve workout history and calculate meaningful performance metrics.
4. Support reusable routines and multi-day training programs.
5. Import structured plans generated by ChatGPT, Claude, or other AI assistants.
6. Import plans from online articles through an assisted extraction workflow.
7. Provide an exercise catalog with guides, muscle groups, equipment information, and available demonstrations.
8. Work offline and retain data across app restarts.
9. Be installable on an iPhone without App Store publication.
10. Avoid mandatory accounts, cloud services, and paid APIs.

### Non-goals

The initial product is not intended to be:

- A social fitness network.
- A commercial SaaS product.
- A personal-training marketplace.
- A medical or rehabilitation application.
- An AI coaching service that requires recurring inference costs.
- A replacement for Apple Health or a comprehensive health platform.
- A native iOS application unless PWA limitations prove unacceptable.
- A clone of every Hevy feature regardless of personal usefulness.

## 2. User Context and Assumptions

The primary user is a senior software engineer who is comfortable with TypeScript, modern web development, databases, and AI-assisted coding.

The developer currently pays for Hevy but primarily uses it as a workout tracker. Advanced commercial features are not a major reason to keep the subscription.

The application should therefore optimize for utility, speed, data ownership, and maintainability rather than broad feature coverage.

### Known constraints

- The primary device is an iPhone.
- Installation should be simple and should not require Xcode or recurring manual signing.
- The application must retain workout history locally.
- Offline usage is important because gym connectivity cannot be assumed.
- Exercise guides and plan data should be reusable without depending on a third-party API being available during a workout.
- The user wants to choose or generate a training plan separately from the workout logger.
- The user is open to using an external AI assistant to generate structured data.
- The app should avoid unnecessary complexity and be achievable as a personal project.

### Initial assumptions to validate during implementation

- A PWA is sufficient for the first version.
- The user is willing to manage their own backups.
- A local database is sufficient; cloud synchronization is not initially necessary.
- A small curated exercise catalog plus a larger imported catalog is acceptable.
- AI-generated plans will be reviewed by the user before becoming active.
- The user may eventually import existing Hevy workout history.
- The interface should be optimized for use during a workout, including one-handed operation.

Do not introduce account management, a backend, or paid APIs merely because they are common in commercial applications.

## 3. Product Principles

### 3.1 Local-first

The local database is the source of truth.

Routine editing, workout logging, history, progress calculations, exercise searches, and plan imports must function without network access once the relevant application assets and catalog data are available.

### 3.2 Fast interaction

The application is used between sets, when the user may be tired, distracted, or holding a phone with one hand.

Common actions should require as few interactions as practical.

Prioritize:

- Starting a workout.
- Marking a set complete.
- Editing weight and reps.
- Seeing previous performance.
- Starting and dismissing rest timers.
- Adding or replacing an exercise.
- Finishing a workout.

### 3.3 Data ownership

Users must be able to export all essential personal data in a portable format.

No essential workout history should be trapped in an application-specific service.

### 3.4 Structured, validated imports

AI-generated content is untrusted input, not executable logic.

All imported programs must pass schema validation, exercise resolution, and user review before being saved.

### 3.5 Progressive enhancement

Implement the simplest version that works reliably.

Use PWA capabilities first. Introduce native code or a backend only when a concrete requirement cannot be met adequately by the local-first architecture.

### 3.6 Clear separation of concerns

Keep the following separate:

- Exercise catalog.
- Program templates.
- Routine templates.
- Scheduled workouts.
- Completed workout sessions.
- Completed sets.
- Progress metrics.
- External import/export formats.

Changing a future routine must not silently rewrite historical workouts.

## 5. Information Architecture

The main navigation should prioritize workout execution over analytics.

Recommended top-level destinations:

1. **Home**
2. **Routines**
3. **History**
4. **Exercises**
5. **Progress**

Settings and import/export can be accessed from the appropriate screens or a secondary menu.

### 5.1 Home

The home screen should answer:

- What workout should I do today?
- What did I last train?
- Can I start my next session immediately?
- How many sessions have I completed recently?

Elements:

- Primary "Start workout" action.
- Today's scheduled routine, when applicable.
- Quick-start for any saved routine.
- Recent workouts.
- Weekly workout count.
- A compact personal-record or progression summary.

Do not make the home screen an analytics dashboard that delays the start-workout action.

### 5.2 Routines

Display saved programs, individual routines, and routine folders.

Support:

- Create program.
- Import program.
- Create routine.
- Edit routine.
- Duplicate routine.
- Delete routine.
- Reorder routines.
- Organize routines into folders.
- Schedule routines.
- Start a workout from a routine.
- Export a program.

### 5.3 History

Show completed workouts in reverse chronological order.

Each workout detail should include:

- Date and start time.
- Duration.
- Routine name.
- Exercises performed.
- Completed sets.
- Weight, reps, and set types.
- Volume and other derived metrics.
- Personal records achieved.
- Notes.

Allow the user to inspect historical performance without accidentally editing it.

Historical edits may be supported, but they must be explicit and must trigger recalculation of derived statistics.

### 5.4 Exercises

Provide searchable exercise metadata, guides, favorites, and custom exercises.

### 5.5 Progress

Provide exercise-specific and aggregate metrics, with simple charts and date ranges.

Avoid excessive statistics that do not help make training decisions.

## 7. Programs, Routines, and Scheduling

The application must distinguish between a **program** and a **routine**.

A program represents an overall training plan, such as an Upper/Lower split.

A routine represents one reusable workout template, such as Upper A.

A scheduled workout is an intended occurrence of a routine.

A completed workout session is the actual historical record of what happened.

### 7.1 Program model

A program should support:

- Name.
- Description.
- Goal.
- Experience level, when specified.
- Days per week.
- Schedule or cycle definition.
- Associated routines.
- Source and attribution.
- Version.
- User customization status.
- Optional progression instructions.
- Optional deload guidance.

The program must remain editable after import.

### 7.2 Routine builder

Users must be able to:

- Add and remove exercises.
- Reorder exercises.
- Duplicate exercises when appropriate.
- Replace exercises.
- Set prescribed sets.
- Set rep ranges.
- Set optional target weights.
- Set rest durations.
- Add exercise notes.
- Configure warm-up sets.
- Configure supported set types.
- Group exercises into supersets.
- Duplicate routines.
- Rename routines.
- Reorder routines within a program.

### 7.3 Routine versus workout changes

A user may change a routine while training.

Provide clear semantics:

- Changes to the current session affect only that session by default.
- Saving changes to the underlying routine is an explicit action.
- Future routine edits must not mutate historical completed sessions.
- If the current session was created from a routine that has since changed, the active session retains its original snapshot.

### 7.4 Scheduling

Support simple recurring weekly schedules.

Do not require a calendar service.

Users must be able to:

- Assign routines to weekdays.
- Reorder training days.
- Leave rest days.
- Start a routine on a different day when needed.
- Skip or reschedule a planned workout without losing the plan.

Initially, scheduling is advisory rather than an enforcement mechanism.

## 8. Workout Logging

This is the highest-priority user interface.

### 8.1 Starting a workout

Users can start a session from:

- A saved routine.
- The home screen's scheduled workout.
- A quick-start action.

Starting from a routine should create a session snapshot, including the prescribed exercises, sets, rep ranges, rest durations, and notes.

Starting a blank workout may be included if straightforward.

### 8.2 Active workout screen

The active workout screen must prioritize:

- Exercise name.
- Previous performance.
- Set number.
- Weight.
- Reps.
- Completion state.
- Rest timer.
- Exercise notes.
- Add-set action.
- Add-exercise action.
- Finish-workout action.

On a typical phone screen, the user should not have to navigate away from the active session to record a set.

### 8.3 Set logging

Each set should support:

- Weight.
- Reps.
- Completion status.
- Set type.
- Optional RPE.
- Optional reps in reserve.
- Optional duration or distance.
- Optional notes.

Weight and reps should be independently editable.

Use sensible defaults:

- Prefill weight and reps from the most relevant previous set.
- Allow quick duplication of a set.
- Allow keyboard dismissal without losing input.
- Avoid accidental completion when a field is tapped.
- Provide undo for recent destructive actions.

Do not mark a set complete merely because the user changed a value.

### 8.4 Previous values

When logging an exercise, display the last completed performance for that exercise.

The user should be able to see previous weight and reps without opening another page.

Support a setting to choose between:

- Most recent performance for that exercise.
- Performance from the same routine, if available.

The default should be the most recent completed performance, unless testing shows the same-routine option is substantially more useful.

### 8.5 Set types

P1 requirements:

- Normal set.
- Warm-up set.
- Drop set.
- Failure set.
- Superset membership.

Keep set types extensible.

Set types must not silently change the meaning of historical data or volume calculations.

### 8.6 Finishing a workout

When finishing a session:

- Persist all completed data.
- Record start and end times.
- Calculate duration.
- Calculate relevant volume and records.
- Display a compact summary.
- Make the session available in History immediately.

If the user leaves an active session, reopening the application must restore it.

If the user closes the application or the operating system suspends it, the app must not lose already recorded sets.

### 8.7 Interrupted workouts

The application must handle:

- Accidental navigation away.
- App reload.
- Browser suspension.
- Device lock.
- Temporary loss of connectivity.
- Incomplete sets.
- Duplicate completion attempts.

Use explicit session state and persist changes promptly.

Do not depend on an unload handler to save the entire workout at the end.

## 9. Rest Timer

### 9.1 Requirements

The rest timer should support:

- Configurable default duration.
- Per-exercise overrides.
- Automatic start after set completion, configurable in settings.
- Pause/resume.
- Add-time control.
- Skip timer.
- Visible remaining time.
- Audible or haptic feedback where supported.
- A manual start action.

### 9.2 Implementation

Use timestamp-based calculations rather than treating a JavaScript interval as the source of truth.

Store a target end timestamp and calculate remaining time as:

`max(0, ceil((endsAt - now) / 1000))`

The display can update periodically, but timer accuracy must not depend on uninterrupted interval execution.

### 9.3 iPhone PWA limitations

A PWA may be suspended while in the background. Ordinary page timers cannot guarantee an alert when the rest period ends if the app is suspended or the phone is locked.

The initial release should:

- Keep timer state persistent.
- Recalculate correctly on return.
- Support foreground alerts.
- Test the Screen Wake Lock API where available.
- Clearly document background limitations.

Do not claim reliable locked-screen alarms until they have been verified on the actual target device.

If reliable background alerts become a hard requirement, investigate native iOS local notifications or a native wrapper.

Push notifications should not be treated as a direct replacement for locally scheduled timer alarms.

## 10. Progress Tracking

### 10.1 Exercise history

Every exercise detail page should expose historical sessions with:

- Date.
- Sets.
- Reps.
- Weight.
- Set type.
- Volume.
- Optional RPE.
- Notes.

Allow selection of an exercise to view its history independently of a specific routine.

### 10.2 Personal records

Initially track:

- Maximum weight.
- Best repetition set.
- Estimated one-rep maximum.
- Highest session volume for an exercise, if useful.

Record definitions must be explicit and consistent.

Avoid comparing incompatible exercise variations without an explicit mapping.

### 10.3 Estimated one-rep maximum

Use a documented estimation formula and apply it consistently.

For example, the Epley formula may be used for suitable repetition ranges:

`estimated1RM = weight × (1 + reps / 30)`

This is an estimate, not a measured maximum.

Avoid extrapolating extreme repetition sets into misleading strength estimates. Document the valid range and allow the formula to be changed later.

### 10.4 Volume

For a conventional weighted set:

`setVolume = weight × reps`

For an exercise:

`exerciseVolume = sum(completedSetVolume)`

Aggregate by session, week, month, or exercise.

Keep bodyweight exercises and duration-based activities separate unless a meaningful calculation is defined.

For unilateral exercises, document whether volume represents repetitions per side or total repetitions. Do not silently double counts.

### 10.5 Charts

P1 or P0 depending on implementation cost:

- Estimated 1RM over time.
- Maximum working weight over time.
- Exercise volume over time.
- Total training volume.
- Training frequency.
- Weekly sets by muscle group.

Charts must use completed historical data and support sensible date ranges.

### 10.6 Muscle-group volume

Use exercise metadata to associate exercises with primary and secondary muscles.

Any volume attribution formula should be documented.

Do not present estimated muscle-group volume as an exact physiological measurement.

### 10.7 Calendar and consistency

Show completed sessions on a calendar.

Optionally calculate:

- Workouts per week.
- Training frequency.
- Consecutive training weeks.
- Monthly workout counts.

Avoid gamification that penalizes planned rest days.

### 10.8 Body measurements

P1/P2:

- Body weight.
- Waist.
- Other user-defined measurements.
- Dated progress photos.

Measurements must be optional and independent of the workout logging workflow.

Progress photos should remain private and local by default.

## 11. AI-Assisted Plan Import

This is a differentiating feature and must be included in the initial product design.

The app must support plans generated by an external AI assistant without requiring an AI API inside the app.

### 11.1 Core workflow

1. User asks an external AI assistant to create or adapt a training plan.
2. The assistant produces JSON matching the app's documented import schema.
3. User copies the JSON.
4. User opens Import Plan in the application.
5. Application parses the input.
6. Application validates the schema.
7. Application resolves exercise identifiers against the local catalog.
8. Unmatched exercises are flagged.
9. User reviews the plan.
10. User edits or accepts the plan.
11. The application saves the program and its routines.
12. The program becomes available for scheduling and workout logging.

No imported plan should become active without explicit user confirmation.

### 11.2 Import input methods

P0:

- Paste JSON.
- Import a `.json` file.

P1:

- Paste Markdown containing JSON.
- Paste CSV.
- Import a documented generic workout file.
- Paste an article or training-plan text.
- Import from a URL with an assisted extraction workflow.

The parser may recognize a fenced JSON block, but it must not silently interpret arbitrary prose as valid JSON without an explicit extraction step.

### 11.3 Import preview

The preview should show:

- Program name.
- Goal.
- Weekly schedule.
- Routines.
- Exercises.
- Sets and rep ranges.
- Rest durations.
- Notes.
- Missing or ambiguous exercises.
- Unsupported fields.
- Validation errors and warnings.

Users should be able to:

- Rename the program.
- Edit exercises.
- Replace unmatched exercises.
- Remove exercises.
- Adjust set counts and rep ranges.
- Change rest times.
- Reorder exercises.
- Save as a new program.

### 11.4 Exercise matching

Use a resolution pipeline:

1. Exact canonical ID match.
2. Exact alias match.
3. Normalized name match.
4. Optional fuzzy matching.
5. Manual selection for unresolved cases.

Fuzzy matching must never silently substitute a materially different movement.

For example, a barbell bench press should not automatically become a dumbbell fly because both involve chest muscles.

The import preview must distinguish exact matches, suggested matches, and unresolved exercises.

### 11.5 Schema validation

Validate:

- Supported schema version.
- Required fields.
- Unique or correctly scoped identifiers.
- Non-empty program and routine names.
- Positive integer set counts.
- Valid rep ranges.
- Non-negative rest durations.
- Valid exercise types.
- Valid schedule entries.
- Correct data types.
- Reasonable field lengths.
- Supported progression definitions.

Warnings should be used for suspicious but potentially valid data.

Errors should prevent saving until corrected.

The application must never evaluate imported code or execute expressions from a plan.

### 11.6 External AI prompt generator

Provide a "Generate a plan with AI" helper that copies a prompt to the clipboard.

The prompt should contain:

- The program schema.
- Allowed exercise identifiers and names.
- The user's selected constraints.
- The requested schedule.
- The desired training goal.
- Equipment and exercise restrictions.
- Required output format.
- Instructions to return JSON only.
- Instructions not to invent exercise IDs.
- Instructions to use supported fields only.

If personal workout data is included, the user must explicitly choose to include it.

Do not automatically upload workout history to an external service.

### 11.7 AI-generated plan quality

The importer validates structure, not scientific quality.

Provide warnings or review prompts for:

- Missing muscle-group coverage.
- Implausible training frequency.
- Unusually high prescribed volume.
- Missing rest guidance.
- Conflicting schedules.
- Exercises requiring unavailable equipment.
- Unsupported progression instructions.

Do not claim that a structurally valid program is safe or optimal.

Avoid automatic medical or injury-related recommendations.

## 12. Online Training-Plan Import

The user should be able to reuse plans from reputable websites without manually reconstructing every exercise.

### 12.1 Desired workflow

1. Paste a URL or training-plan text.
2. Retrieve the content where possible.
3. Extract structured exercise information.
4. Map exercises to the local catalog.
5. Present the proposed program for review.
6. Allow customization.
7. Save the result as a normal editable program.

### 12.2 Retrieval limitations

Websites may block cross-origin requests, require JavaScript, use dynamic layouts, or restrict automated retrieval.

Therefore:

- URL import must not be assumed to work for every site.
- Offer paste-text fallback.
- Do not bypass authentication or access controls.
- Do not scrape private content.
- Preserve source URLs and attribution.
- Avoid downloading or redistributing copyrighted media without permission.

### 12.3 AI extraction

AI extraction can be integrated later without changing the canonical program schema.

If no AI API is configured, the user must still be able to import JSON or enter a plan manually.

The extraction interface should make clear which fields were inferred and which were explicitly present in the source.

## 13. Data Import, Export, and Backup

### 13.1 JSON export

P0.

Provide a complete application backup containing:

- Exercises and custom exercises.
- Programs.
- Routines.
- Routine scheduling.
- Workout sessions.
- Completed sets.
- Exercise notes.
- Relevant settings.
- Body measurements, if enabled.
- Schema and export version.

Use a documented, versioned format.

### 13.2 JSON import

Support:

- Full backup restore.
- Program-only import.
- Routine-only import.

These are different operations and must not be confused.

Full restore must warn before replacing existing data.

Program-only imports should add a program without overwriting unrelated workout history.

### 13.3 CSV

P1.

Support exporting workout history into a spreadsheet-friendly format.

Include enough information to reconstruct completed sets, with stable identifiers and timestamps.

CSV imports must define column mappings and handle duplicate records deliberately.

### 13.4 Hevy migration

Investigate Hevy's official workout-history export and current API documentation.

Useful references:

- https://www.hevyapp.com/
- https://api.hevyapp.com/docs/

Do not assume that all historical data is available in every export format or subscription tier.

Implement migration as a separate adapter:

`Hevy export → normalized import records → validation → user preview → local database`

Requirements:

- Preserve original workout dates.
- Preserve exercise names.
- Preserve sets, reps, weights, and supported set types.
- Preserve notes where available.
- Report unsupported fields.
- Detect likely duplicate sessions.
- Never overwrite existing history silently.

Do not make the core application depend on Hevy's API.

### 13.5 Backup guidance

IndexedDB is persistent local storage, but it is not a substitute for an independent backup.

The app should provide:

- An accessible export action.
- A clear backup reminder or backup status.
- Restore instructions.
- Error handling for corrupt or incompatible backups.

No backup should silently fail.

## 14. Technical Architecture

### 14.1 Recommended stack

Use the following defaults unless the repository already contains a compelling alternative:

| Layer | Technology |
|---|---|
| Language | TypeScript |
| UI | Svelte 5 via SvelteKit (static SPA) — changed from React, see ADR 0002 |
| Build tool | Vite (via SvelteKit) |
| Styling | CSS modules, plain CSS, or the project's existing styling system |
| Local database | IndexedDB |
| Database wrapper | Dexie |
| Validation | Zod |
| Offline app shell | SvelteKit service worker |
| PWA | Web app manifest + SvelteKit service worker |
| Charts | Lightweight charting library, introduced only when needed |
| Testing | Vitest and Testing Library for Svelte |
| Browser automation | Playwright, if supported by the development environment |

Do not use Next.js merely because it is familiar. Server-side rendering and backend features are not required for the initial product.

Do not add a server, database service, authentication provider, or cloud infrastructure unless a requirement demands it.

### 14.2 Architecture boundaries

Recommended modules:

- `catalog`
- `programs`
- `routines`
- `sessions`
- `logging`
- `timers`
- `progress`
- `imports`
- `exports`
- `storage`
- `settings`

Separate domain logic from UI components.

The application should be testable without rendering the interface.

### 14.3 Data access

Use a dedicated repository or service layer around Dexie.

UI components should not contain arbitrary database queries or duplicate business logic.

Examples:

- `ExerciseRepository`
- `ProgramRepository`
- `RoutineRepository`
- `WorkoutSessionRepository`
- `ProgressService`
- `ProgramImportService`
- `BackupService`

Keep abstractions pragmatic. Do not introduce a generic enterprise repository framework.

### 14.4 Database migrations

Use explicit schema versions and migration procedures.

Requirements:

- Preserve existing workout history across upgrades.
- Never drop user data as part of an ordinary application update.
- Test migrations against representative old database states.
- Provide error handling for failed upgrades.
- Keep export/import compatibility independent from the IndexedDB schema.

### 14.5 PWA requirements

- Valid web app manifest.
- Appropriate application icons.
- HTTPS deployment.
- Service worker caching for application assets.
- Offline startup after successful initial loading.
- No network requirement for workout logging.
- Correct viewport and safe-area handling.
- Installation instructions for iPhone Safari.
- Testing on a physical iPhone.

The service worker should not cache dynamic API responses indiscriminately.

### 14.6 Backend policy

No backend is required for the initial release.

Potential future reasons to add one:

- Cloud backup.
- Cross-device synchronization.
- Shared program hosting.
- Built-in AI inference.
- Remote push infrastructure.

Each requires a separate architectural decision.

## 15. Canonical Data Model

The following is a logical model, not a requirement to use these exact TypeScript types. The coding agent should refine it based on implementation details while preserving the domain boundaries.

### 15.1 Exercise

```ts
type Exercise = {
```

### 15.11 Data-model rules

2. Editing an exercise's display name must not corrupt historical records.

4. Use stable IDs rather than exercise names as foreign keys.

6. Use a documented convention for weight units.
7. Store raw set records and calculate aggregates.

9. Preserve unknown fields when safely possible during import/export version upgrades.
10. Do not introduce user accounts or synchronization fields without a concrete need.

## 16. Versioned Program Import Schema

The program-import format is a public contract between the application and external AI assistants.

Keep it independent from the internal IndexedDB schema.

The importer should translate the external format into domain entities.

### 16.1 Example

```json
{
  "schemaVersion": 1,
  "program": {
    "name": "Upper / Lower Hypertrophy",
    "description": "Four-day strength-training program",
    "goal": "muscle_gain",
    "experienceLevel": "intermediate",
    "daysPerWeek": 4,
    "schedule": {
      "type": "weekly",
      "days": [
        { "day": "monday", "routine": "upper_a" },
        { "day": "tuesday", "routine": "lower_a" },
        { "day": "thursday", "routine": "upper_b" },
        { "day": "friday", "routine": "lower_b" }
      ]
    },
    "routines": [
      {
        "id": "upper_a",
        "name": "Upper A",
        "exercises": [
          {
            "exercise": "barbell_bench_press",
            "sets": 3,
            "repRange": [6, 10],
            "restSeconds": 150,
            "notes": "Use controlled repetitions"
          },
          {
            "exercise": "lat_pulldown",
            "sets": 3,
            "repRange": [8, 12],
            "restSeconds": 120
          }
        ]
      }
    ]
  }
}
```

This example illustrates the format and is not intended as a medically validated training prescription.

### 16.2 Schema design requirements

The external schema should support:

- Program metadata.
- Routines.
- Ordered exercises.
- Set counts.
- Rep ranges.
- Optional target loads.
- Optional rest durations.
- Notes.
- Supported set types.
- Optional RPE/RIR targets.
- Optional weekly scheduling.
- Optional progression rules.
- Source and attribution metadata.

Do not require every optional field.

### 16.3 Stable exercise identifiers

Use stable, documented identifiers.

The import prompt may include an abbreviated catalog, but the full catalog remains in the app.

If an exercise cannot be identified, allow an unresolved name or explicit custom-exercise proposal in the import format. Resolve it during preview rather than fabricating an ID.

### 16.4 Version compatibility

- Reject unsupported major schema versions with a clear message.
- Validate each supported version using its own schema.
- Migrate older supported versions to the current domain model.
- Include export-version metadata.
- Test compatibility with previously exported files.

### 16.5 Import security

Treat all imported content as untrusted.

- Never execute code from JSON.
- Do not render imported HTML directly.
- Sanitize URLs and text where relevant.
- Reject malformed structures.
- Enforce reasonable size limits.
- Avoid unbounded recursive structures.
- Do not automatically fetch arbitrary media URLs during parsing.
- Do not allow imported data to overwrite the database without user confirmation.

## 17. Progression Rules

Progression should be configurable and transparent rather than presented as AI coaching.

### 17.1 Initial supported approach

A routine may prescribe a rep range, such as 8–12 reps.

An optional double-progression rule may recommend increasing the load after the user consistently achieves the upper end of the range across the prescribed sets.

The exact rule must be configurable.

Do not automatically change prescribed loads in the first release.

### 17.2 Future rules

Potential future support:

- Double progression.
- Fixed load increments.
- Percentage-based progression.
- RPE/RIR-guided progression.
- Deload scheduling.
- User-defined rules.

Every suggestion should explain the rule that produced it.

The user must retain control over whether to apply a suggested change.

## 25. Coding-Agent Instructions

The coding agent should follow these rules.

### 25.1 Work incrementally

Do not attempt to implement every feature in one giant change.

Build a working vertical slice first:

1. Start a routine.
2. Record a set.
3. Persist it.
4. Reload the app.
5. Recover the session.
6. Finish the workout.
7. Inspect history.

Then expand the feature set.

### 25.2 Inspect before editing

- Read the existing project structure.
- Reuse existing tooling when appropriate.
- Identify missing requirements.
- Avoid unnecessary dependency additions.
- Explain architectural decisions that affect data persistence.

### 25.3 Keep business logic testable

Progress calculations, exercise matching, import validation, and persistence behavior should not depend on React components.

### 25.4 Avoid premature infrastructure

Do not add a backend, account system, paid API, or synchronization layer without a concrete requirement.

### 25.5 Preserve data

Data loss is a serious defect.

Test migrations, interrupted sessions, and restore behavior before declaring the database layer complete.

### 25.6 Keep the app usable throughout development

After each phase, the app should run locally and the completed features should remain functional.

### 25.7 Document decisions

Maintain:

- README with setup and deployment instructions.
- Data-model documentation.
- Import schema documentation.
- Backup and restore instructions.
- PWA installation instructions.
- Known browser limitations.
- Exercise-data attribution.
- A short record of important architectural decisions.

### 25.8 Do not overbuild

When uncertain, prefer the simplest implementation that meets the requirements.

Do not introduce abstractions, services, or dependencies that solve hypothetical future problems.

## 26. Open Decisions

These questions should be resolved when they materially affect implementation, but should not block the initial architecture.

1. **Application name:** LiftLog is a placeholder.
2. **Visual direction:** Choose a compact, polished fitness interface; final branding is open.
3. **Initial training program:** The app should support any valid program, independently of which routine the user ultimately chooses.
4. **Catalog coverage:** Decide how much wger data to bundle after inspecting its quality and licensing.
5. **Hevy migration:** Inspect an actual export before defining the migration adapter.
6. **Timer behavior:** Determine whether foreground alerts are sufficient or reliable locked-screen alerts are mandatory.
7. **Weight units:** Use kilograms as the initial default, with configurable units.
8. **Backup policy:** Start with manual JSON backups and consider reminders later.
9. **Native iOS:** Defer unless real-device testing identifies an important unmet requirement.
10. **Cloud synchronization:** Defer until a concrete need arises.
11. **Built-in AI:** Do not include in the first release.
12. **Online-plan extraction:** Start with pasted text and structured imports before building arbitrary URL extraction.
