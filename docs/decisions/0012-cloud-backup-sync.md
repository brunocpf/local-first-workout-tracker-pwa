# 0012 – Cloud backup and multi-device sync

**Status:** proposed (recommendation; the owner confirms the open questions below) · 2026-10-21

**Context:** PRD §14.5 and AGENTS.md allow no backend, accounts or sync without a concrete requirement and an ADR (the only backend is the optional push relay, [ADR 0014](0014-rest-timer-push.md), which never sees workout data). PRD §20 says no data is uploaded automatically and that if sync is ever added we must document exactly what leaves the device and obtain consent. PRD §15 says "no accounts or sync fields", and the backup is a manual versioned JSON file ([backup-restore.md](../backup-restore.md)) with a reminder banner. IndexedDB is not a backup: it can be evicted, is bound to the origin, and on iOS the installed app and the Safari tab have separate storage ([browser-limitations.md](../browser-limitations.md)). Two different needs hide behind "cloud":

- **Off-device backup** (protection against losing the phone or the data). A copy is enough; no merging.
- **Multi-device sync** (log on the phone, review or plan on the laptop; PRD §2 says the user "sometimes reviews or plans on a laptop"). Two writable replicas must merge.

Today the laptop path is export on one device and a full restore (which *replaces* everything) on the other. That is a one-way copy, not sync, and it is fine for occasional review. There is no recorded case of lost data or of a missed workout caused by the lack of sync.

Third-party facts below were read on 2026-10-21 from the pages cited; limits and prices change, so re-check before building anything.

**Options evaluated**

1. **Status quo: manual backup via the share sheet + reminders (current).**
   - Mobile uses Web Share with a file (Files, iCloud Drive, Google Drive, …), desktop downloads; the banner reminds after `backupReminderDays` / `backupReminderSessions`. If the user saves the file into a synced folder (iCloud Drive, Drive, Dropbox), the OS client already makes it an off-device copy, with no code, no account of ours and no new network origin.
   - Cost: zero. Privacy: nothing leaves unless the user chooses where to put the file.
   - Weakness: it depends on the user acting; the reminder is the only nudge, and it is only seen when the app is opened. Restore is all-or-nothing, so it is not multi-device.
2. **User-owned storage via OAuth, client-side only (no backend).** The PWA gets a token and uploads the existing backup JSON to a private app folder in the user's own Google Drive, Dropbox or OneDrive.
   - *Google Drive:* the `drive.appdata` scope is documented as non-sensitive, and the app data folder is hidden from the Drive UI and only readable by the app that created it ([appdata guide](https://developers.google.com/workspace/drive/api/guides/appdata), updated 2026-09-03). But the browser flow is the token model: "there is no need to store per-user refresh tokens", tokens are short-lived, and getting a new one must start from a user gesture, only in a popup dialog ([token model](https://developers.google.com/identity/oauth2/web/guides/use-token-model), updated 2026-05-26). So an upload can happen right after a gesture (e.g. "Back up now", or finishing a workout, if a token is still valid) but a truly silent background backup is not possible from a web page. A Google Cloud project with a consent screen is needed; verification is required for public apps that request sensitive or restricted scopes ([production readiness](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview), updated 2026-05-22), so a non-sensitive scope should not need it, though the page does not say so outright (**unverified**). A project left in "Testing" is capped at 100 test users and its refresh tokens expire in 7 days ([OAuth 2.0 overview](https://developers.google.com/identity/protocols/oauth2), updated 2026-10-16); the token model issues no refresh tokens, so the 7 days do not matter here. The origin `brunocpf.github.io` is shared with other project sites (ADR 0003), so an OAuth client registered for it is exposed to all of them.
   - *Dropbox:* App Folder permission type limits the app to its own folder. For pure-JS single-page apps Dropbox recommends the PKCE code flow with short-lived access tokens and no refresh tokens, so it has the same "user must re-authorize" limit; refresh tokens (`token_access_type=offline`) are recommended for native/background clients ([Dropbox OAuth guide](https://docs.dropboxapi.com/dropbox-api/docs/oauth), no page date). Browser CORS support for the API was not stated on the pages read: **unverified**.
   - *OneDrive:* app folder (`Files.ReadWrite.AppFolder`), but it is a normal visible folder under Apps that users can edit ([docs](https://learn.microsoft.com/en-us/onedrive/developer/rest-api/concepts/special-folders-appfolder), updated 2026-05-14). SPA refresh-token lifetimes were not found in those docs: **unverified**.
   - *iCloud:* there is no plain file API for web apps; CloudKit JS would need an Apple Developer Program membership ($99/year per [apple.com/programs](https://developer.apple.com/programs/)) and an Apple ID on every device, which Android and desktop Chrome users do not have. Not evaluated further.
   - Common costs: provider SDK/script and API hosts must be added to the CSP (`connect-src`, and `script-src` for Google's script), which is the largest weakening of ADR 0003's exfiltration guard (a single allow-listed host per provider, never `https:`); a token in `localStorage` is readable by any script on the origin (same exposure as ADR 0013 option 2), so tokens must be excluded from backups and never logged; one more provider-specific code path to maintain.
   - Result is backup only. Two devices pushing to the same file means last writer wins; no merge.
   - Cost: no money. Privacy: the full history leaves the device, to the user's own account at a third party, only when they connect and trigger it.
3. **End-to-end encrypted blob storage on our own backend.** The app encrypts the backup with a key derived on-device and uploads the ciphertext to a small service.
   - Needs a store: Cloudflare R2's free tier is 10 GB-month storage, 1 M Class A and 10 M Class B requests per month, free egress (Standard storage; [R2 pricing](https://developers.cloudflare.com/r2/pricing/), updated 2026-10-01), far more than one person's backups need. Money is not the obstacle.
   - The obstacles are everything else: an identity or capability token to keep strangers from filling the bucket (the relay of ADR 0014 gets by with an origin check and rate limit only because each request is tiny and carries nothing of value), key management (a lost passphrase means lost backups, a stored key defeats the point, and the Web Crypto API offers PBKDF2 but no memory-hard KDF, so a password-derived key is weaker than it looks or needs a WASM Argon2 dependency), a second deploy the owner must operate, and the same CSP widening as option 2. It would be the first server to hold the user's workout history, ciphertext or not (IP, size, timing visible), which is a different category from ADR 0014.
   - Still backup only unless a merge protocol is added. **Rejected for now.**
4. **Multi-device sync (CRDT library or sync engine).**
   - A CRDT library (Automerge, Yjs) merges edits without a central winner but needs a transport and a server anyway, and a CRDT document is a different data model from our Dexie tables (relational by stable ids, raw sets, snapshots). Merged conflicts are resolved silently, which is a bad default for logged weights and reps. Generic references: [2026 guide on CRDT libraries vs sync engines](https://devtoollab.com/blog/local-first-apps-crdt-sync-engine-guide-2026); no source specific to Dexie was found, so how well a CRDT would fit our tables is a design question, not a finding.
   - Dexie Cloud is the closest fit (same Dexie library). It is a hosted service with built-in auth (passwordless email OTP); its pricing page lists a free tier with 3 production users and 100 MB, and €0.12 per user per month beyond ([dexie.org/cloud/pricing](https://dexie.org/cloud/pricing), no page date; the page also says €3 per 25 seats, consistent with that, and evaluation users stop syncing after 30 active days). Free for one person, but it means an account with a third party, all history on their servers, vendor lock-in, and a possible schema change (sync services generally need globally unique string ids and tombstones for deletes; whether our ids and `exerciseIds` index qualify is **unchecked**).
   - Even with a sync engine, the app's own invariants need decisions: one active session (what if two devices start workouts offline?), the rest timer and relay (ADR 0014) are per-device, `restore` is a full replace, backup format v3 has no tombstones, `lastBackupAt` and settings are per-device, and migration `upgrade` functions would run against synced data from older app versions on the other device.
   - Cost: for one user, near zero money, large complexity. **Rejected for now.**
5. **Do more locally instead.** Cheaper nudges that need no network: persistent-storage status (already shown), the backup reminder (already built), and, if wanted, a "Backed up to a synced folder?" hint on the success message after a Share/save. WebKit says it grants `persist()` using heuristics such as whether the site is a Home Screen web app, and that persistent-mode origins are excluded from eviction ([WebKit storage policy, 2023-08-10](https://webkit.org/blog/14403/updates-to-storage-policy/)); that page gives no figure for an inactivity cap, so the iOS eviction behaviour stays a device check (browser-limitations.md).

**Decision (recommended):**

1. **Do not build cloud backup or sync now.** Keep option 1: manual versioned JSON backup, Web Share to a folder the user picks, and the reminder. No new origin in `connect-src`, no account, no tokens, no sync fields in the data model. PRD §14.5 and AGENTS.md stay as written: the push relay is still the only backend.
2. **Recommend a synced folder, not a service.** The backup UI/docs should keep telling users that saving the file to iCloud Drive, Google Drive or Dropbox *is* the off-device copy. Nothing to build for this today.
3. **Laptop use stays export → restore (replace)**, which is acceptable for occasional review. If two-way use becomes a real need, that is a new ADR about sync, not an extension of this one.
4. **If a concrete need appears, build in this order, one ADR each:**
   - *First, option 2 as backup only:* upload the existing `backupV3` file to one provider's private app folder, user-initiated (a button, a gesture is required anyway), opt-in, off by default. Start with the provider the owner already uses; Google Drive `drive.appdata` is the best documented. This costs no server and no money, reuses the validated format and restore path unchanged, and changes no data model.
   - *Only then,* if two-way use is still wanted, evaluate sync (option 4) against real conflict cases, with a design for active sessions, deletes and migrations.
   - Option 3 only if option 2 cannot meet a concrete requirement (e.g. no suitable provider), and then with an explicit key-loss story.
5. **Requirements any future version must meet (PRD §20):** opt-in and off by default; the app works fully offline and without it; a consent screen stating exactly what is sent (the whole history, including measurements, notes and settings, in an unencrypted file at the provider unless encrypted) and where; visible status (last uploaded, error) and a way to disconnect and delete the remote copy; exactly one allow-listed host per provider in `connect-src` (never `https:`) and the provider script allowed only when enabled; tokens and connection state kept out of IndexedDB-backed backups and never logged; restore from the cloud goes through the same `parseBackup` validation and confirmation as a file; remote copies are untrusted input (size limit, Zod, never evaluated); failures never block logging; backup files are never at public URLs.

**Triggers to revisit:** the owner loses or nearly loses data because a manual backup was stale; the reminder proves ignored in practice; or the owner regularly wants to log on one device and continue on another. Cost is not a trigger: the free tiers above would cover one person.

**Open questions for the owner:**
- Is the laptop mainly for viewing and planning (then the status quo is enough), or do you want to log workouts on it too (then sync is a real requirement)?
- Has the manual backup flow actually been missed or ignored since you started using the app? If so, a user-initiated Drive/Dropbox upload (decision item 4) is the first thing to add.

**Follow-ups (only if approved, create then):** (a) provider app-folder upload/download behind a feature flag, with CSP change, consent screen and tests against the existing backup fixtures; (b) device checks for the popup/token flow in the installed iOS app, which is unverified; (c) a sync design ADR with a conflict model for sessions, deletes and the active session.

**Consequences:** No code, bundle size, CSP or data format changes. Backups stay a plain file the user controls, and the cost is that off-device copies and multi-device use depend on the user. The recorded evaluation lets a later need start from option 2 instead of re-researching.
