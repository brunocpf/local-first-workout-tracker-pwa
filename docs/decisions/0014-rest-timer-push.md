# 0014 – Rest-timer push notifications via a minimal Web Push relay

**Status:** accepted · 2026-10-20 (amends the "no backend" rule for this one purpose)

**Context:** A web page cannot run timers in the background: iOS suspends it (no background timers, no `navigator.vibrate`), Android throttles it, and service workers have no timed alarms (ADR 0005, docs/browser-limitations.md). The only web-native way to alert at a chosen moment is a Web Push sent at that moment by a server. Web Push works on iOS/iPadOS 16.4+ **only for a PWA added to the Home Screen** (permission requested from a user gesture), and in Android Chrome and desktop browsers. AGENTS.md and PRD §14.5 otherwise forbid a backend; the owner uses the installed PWA and wants locked-screen rest alerts, so there is now a concrete requirement. The alternative route (a native wrapper) is the separate decision in #103.

**Options evaluated** (free-tier figures checked on 2026-10-20 against the provider pages cited; re-check at deploy time)

1. **Cloudflare Workers + Durable Object alarm (chosen).** One Durable Object per device stores `{endpoint, fireAt}` and sets an `alarm()` for that instant; the alarm sends the push and forgets everything. No polling or cron. Workers Free: 100,000 requests/day and 10 ms CPU per request ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)); waiting on `fetch` and WebCrypto signing is cheap. Durable Objects on Free (SQLite backend only): 100,000 requests/day including alarm invocations, 13,000 GB-s/day, 5 M rows read and 100,000 rows written/day (each `setAlarm()` is one row written), 5 GB storage; exceeding a limit makes further operations fail until 00:00 UTC ([DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)). One person needs a few hundred of each per day. Alarms have at-least-once execution with retries on a thrown error ([DO alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)); the docs give no precision figure, so second-level accuracy is a device check (#196). Rate limiting binding: `period` of 10 or 60 s, per Cloudflare location, deliberately approximate ([rate limit binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)); its availability on the Free plan is not stated, so the relay treats it as optional. Cost: a Cloudflare account.
2. **Cloudflare Cron Triggers / Queues.** Cron Triggers are minute-granular, too coarse for a 90 s rest. Queues are now on the Free plan (10,000 operations/day, about 3 per delivered message, fixed 24 h retention; [changelog 2026-02-04](https://developers.cloudflare.com/changelog/2026-02-04-queues-free-plan/)) and `delaySeconds` allows up to 24 h ([Queues limits](https://developers.cloudflare.com/queues/platform/limits/)), so a delayed message could carry the push. But a queued message can't be cancelled or moved: pause, skip and ±15 s would each need a cancellation record checked at delivery, which brings back stored state and more operations. Viable but more complex than an alarm that is simply replaced. Not chosen.
3. **Deno Deploy (Deno KV `enqueue` with `delay`).** KV queues do support durable delayed delivery (`delay` in ms, at-least-once, retried; [Deno queues](https://docs.deno.com/deploy/kv/manual/queue_overview/)); free plan 1 M requests, 1 M KV reads and 500 k KV writes per month ([Deno pricing](https://deno.com/deploy/pricing)). Same cancellation problem as Queues. Decisive: Deno announced on 2026-10-09 that Deno Deploy shuts down six months later as Deno joins Cloudflare ([Deno blog](https://deno.com/blog/cloudflare)). Rejected.
4. **Supabase Edge Functions + pg_cron.** pg_cron schedules are minute-level by default and the setup adds a database that stores rows. Coarser and heavier than option 1. Rejected (not re-measured).
5. **GitHub Actions.** Scheduled workflows run at most every 5 minutes and start late; not viable. Rejected.
6. **ntfy.sh or similar public services.** ntfy delivers through its own app / its own web client; it cannot send a Web Push to *this* PWA's subscription without being a relay for it, and its delayed delivery puts the topic name and content on a public service. Rejected.
7. **Do nothing** (foreground alerts only). Remains the fallback whenever the relay is missing or unreachable.

**Decision:**
1. Build the relay on Cloudflare Workers + Durable Objects in a top-level `relay/` folder, outside the SvelteKit build and deployed separately by the owner (`relay/README.md`).
2. **The exception to the no-backend rule is exactly this relay.** AGENTS.md and PRD §14.5 now read: no backend except the minimal push relay of this ADR. Any other backend still needs its own ADR.
3. **The relay stores nothing but a push endpoint and a fire time**, per random per-device id, deleted when it fires or is cancelled. It never receives workout data, exercise names, durations or user identity. The push has **no payload** (so no RFC 8291 encryption keys are even needed and the subscription's `keys` are not stored); the service worker shows a fixed "Rest over" notification. The relay and push services see the device's push endpoint, the IP address and the timing of rest timers.
4. **Optional and opt-in.** Off by default; the app is fully functional without it. The relay URL and VAPID public key are build-time settings (`VITE_PUSH_RELAY_URL`, `VITE_PUSH_VAPID_PUBLIC_KEY`, repo variables in the deploy workflow); unset, the feature is hidden (no Settings section, no timer hint). The CSP `connect-src` is widened to that single relay host only when set (ADR 0003). The subscription is kept in `localStorage`, never logged and never in a backup; only the `restNotifications` flag is in settings and backups.
5. **Abuse and limits:** requests only from the single allowed origin (CORS plus a server-side check), Zod validation, 4 KB body limit, `fireAt` at most 2 h ahead, endpoints restricted to https push-service hosts (FCM, Mozilla, Apple, Windows) so the relay cannot be aimed at arbitrary URLs, per-IP rate limit, no accounts. VAPID private key lives only as a Worker secret.
6. **Duplicates and failure:** the app schedules at `endsAt`, cancels or reschedules on pause/skip/adjust/finish/discard, and cancels shortly (3 s) before the end while the page is visible (reverting to a schedule if the page is hidden again), so the foreground alert and the push do not both fire. Requests are serialized and a request superseded while waiting is dropped, so the relay always ends with the latest intent. A relay or network failure is ignored; a failed push is not retried (a late rest alert is worse than none). Known gaps (docs/browser-limitations.md): locking the screen in the last 3 s may give no notification on iOS, and a rate-limited request leaves the previous schedule in place.
7. **Install requirement is explained in the app** (Settings section and a hint beside the timer): background notifications only work for the installed app, notably iOS Add to Home Screen first.

**Follow-up (not done):** handle `pushsubscriptionchange` in the service worker (re-subscribe and store the new subscription). Until then, if a browser rotates the subscription, notifications stop silently until the user turns them off and on again in Settings.

**Consequences:** one small external service the owner must deploy (#196) and a service-worker `push`/`notificationclick` handler. Real-device verification (iPhone and Android, screen locked) is tracked in #196. If the relay is ever dropped, removing the feature touches `src/lib/push.ts`, the settings section, the timer bar effect, the service-worker handlers and `relay/`.
