# 0010 – Progress photos (local-only)

**Status:** proposed (recommendation; the owner confirms the open question below) · 2026-10-20

**Context:** PRD §4 lists progress photos as P2. PRD §20 says no data is uploaded automatically; §13 and ADR 0004 say IndexedDB is persistent but not a backup, and [browser-limitations.md](../browser-limitations.md) says storage can be evicted (iOS: the installed app and the Safari tab have separate storage). Body measurements (T8.15) already live in a `measurements` table and in backup format v2. The question is whether, and how, to keep photos on the device without a backend, and what that does to the backup. Size figures below are estimates for a 1280 px JPEG and must be re-measured when implemented.

**Findings**

- **Storage cost.** A phone photo is 2–5 MB (HEIC/JPEG, 12 MP and up). Re-encoded to a 1280 px longest edge at JPEG quality 0.8 it is roughly 150–300 KB, plus a 320 px thumbnail of about 15 KB. Three poses a week for a year is about 150 photos, so about 30–50 MB; five years is about 200 MB. IndexedDB stores `Blob`s natively (no base64 inflation) and Dexie can hold them in a normal table. Unscaled originals would reach GBs within a year and are not worth keeping. The grid must read the thumbnail blob, never decode full images.
- **Eviction.** Eviction is per origin, so photos are lost together with workouts; they are not a separate risk, but they raise quota use (which makes `persist()` denial and iOS storage pressure more likely) and they are the data users can least recreate. The JSON backup is small and cheap to take often; a photo archive is large and will be taken less often, so photos need their own "not backed up" status instead of sharing the JSON reminder.
- **Backup format.**
  - *Base64 in the JSON backup:* +33% size, the whole file is read, parsed and Zod-validated in memory (`MAX_BACKUP_BYTES` is 50 MB, about 150 photos), every routine backup grows, and iOS memory limits make a failure likely. Rejected.
  - *Separate archive:* photos stay out of the JSON backup (format stays v2, no bump, no change to restore), and users who never take photos pay nothing. Chosen.
  - *OPFS or File System Access:* OPFS is not in a Dexie transaction and has the same eviction behaviour, so it adds a second store without a durability benefit; File System Access is unavailable on iOS and Firefox. Rejected.
- **Privacy.** Photos are the most sensitive data the app could hold. They must never leave the device automatically, never be cached by the service worker, never appear in URLs, and carry no location: re-encoding through a canvas drops EXIF (GPS, device, original timestamp). Archives are unencrypted files the user places in Files/iCloud/Drive, so the UI must say so when exporting. No app lock, no encryption, no gallery integration beyond the OS share sheet.
- **iOS camera and file input.** Without a native wrapper the only camera path that works on every target is `<input type="file" accept="image/*">`. On iOS/iPadOS Safari it opens a sheet (Photo Library / Take Photo / Choose File) and needs no permission prompt; adding `capture` skips the sheet and removes the library choice, so we leave it off (Android and desktop behave similarly or fall back to a file dialog). `getUserMedia` would need a camera permission, an in-app viewfinder and is flaky in standalone mode on iOS: not used. Safari is expected to hand JPEG to the page for `image/*` (HEIC is transcoded); _verify_ on a real device, and if decoding fails show an error and store nothing. Decode with `createImageBitmap(file, { imageOrientation: 'from-image', resizeWidth })` where supported, else an `<img>` + canvas; process files one at a time because very large photos (48 MP) can exceed iOS canvas/memory limits (_verify_). Orientation must be correct in the stored JPEG since EXIF is dropped.

**Decision (recommended):**

1. **Adopt progress photos, strictly local, as an optional P2 feature.** Nothing is uploaded, there is no backend, and the app works fully without photos. Build it only after body measurements (T8.15/T8.16) and with item 4 below; do not ship capture without archive export.
2. **Store resized JPEGs in IndexedDB.** A new `progressPhotos` table in the next Dexie version (additive, no `upgrade`, like version 2): `{ id, takenAt (ISO UTC), timeZone, pose: 'front' | 'side' | 'back' | 'other', note?, image: Blob (image/jpeg, longest edge ≤ 1280), thumb: Blob (≤ 320), width, height, bytes }`, indexed by `takenAt`. Photos are independent of sessions and measurements (the Progress screen can show them on one timeline). Validate metadata with Zod (note ≤ 1000 characters, same rules as measurements); object URLs are created on demand and revoked. Originals are never kept.
3. **Keep photos out of the JSON backup.** `backupVersion` stays 2. Consequences, to be written into `docs/backup-restore.md` and `data-model.md` at implementation: a full JSON restore does not touch `progressPhotos` (it is outside the restore transaction); "delete all data", if offered, must include photos; Settings shows photo count and size next to the storage estimate and warns above about 100 MB or when the quota estimate is above 80%.
4. **Separate "photos archive" for backup and restore.** A store-only ZIP (JPEGs are already compressed) named `workout-photos-YYYY-MM-DD.zip` with `manifest.json` (`photosVersion: 1`, app, `exportedAt`, per-photo metadata and file name) and `photos/<id>.jpg`; thumbnails are regenerated on restore. Small hand-written ZIP writer/reader in `src/lib` (CRC-32 + local headers + central directory; no dependency), assembled as a `Blob` of parts so memory stays low. Saved with Web Share files, else download (as for the JSON backup). Restore is additive and merges by `id` (existing ids are skipped, nothing is deleted or replaced), after validating the manifest with Zod, size/count limits and file names looked up by exact match only (never extracted to a path, never evaluated). It follows the same "validate everything, then one transaction, otherwise nothing changes" rule as the JSON restore. The UI shows "N photos not in an archive" and a separate, dismissible reminder.
5. **Capture UX.** A file input without `capture`, `multiple` for library import, pose picker, date defaulting to now and editable (for photos taken earlier). A compare view (two photos side by side) and delete are in scope; sharing single photos, cropping, filters, overlays and AI body analysis are not.

**Alternatives considered:** do not build it (a valid outcome if the owner prefers; users can keep photos in the OS Photos app, which is already durable and backed up, and this feature mostly adds a place to look at them next to measurements); base64 in the JSON backup, OPFS, `getUserMedia`, a native wrapper camera, cloud storage (all above or out of scope, PRD §4/§14.5).

**Open question for the owner:** is the value of in-app photos worth a second backup artifact and the privacy surface? If not, record "not built" here and leave P2 as is. Also confirm that unencrypted archives are acceptable.

**Follow-ups (only if approved, create then):** (a) `progressPhotos` table, Dexie version bump, repository and Zod schema with tests; (b) image pipeline (decode, orientation, resize, thumbnail) with iOS device checks recorded in browser-limitations.md; (c) ZIP archive writer/reader, photos export/restore with fixtures and interrupted-restore tests; (d) capture UI, gallery by date, compare view; (e) storage usage and "not backed up" reminder in Settings; (f) docs: backup-restore.md, data-model.md, privacy notes in PRD §20.

**Consequences:** No code, bundle size or data format changes today. If approved, backups stay small and unchanged for everyone without photos, photos cannot silently inflate or break the JSON backup, and the cost is a second, explicit backup path the user has to use.
